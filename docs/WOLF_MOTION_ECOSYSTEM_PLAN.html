خطة منظومة WOLF Motion Ecosystem

منظومة إنتاج بصري سينمائي تعمل دون اتصال، توحّد عدة محركات متخصصة تحت إدارة مركزية واحدة، بحيث يؤدي كل محرك المهمة التي يتفوّق فيها، ثم تُجمع النتائج في خط إنتاج فيديو موحّد.

خطة معتمدة للتنفيذ بعد اكتمال المراجعة الحالية واختبار Debug وتوجيه المستخدم

1. حالة الوثيقة وحدودها

  • هذه وثيقة تخطيط معماري مستقبلية وليست إعلانًا عن تنفيذ المحركات.
  • موعد بدء التنفيذ: بعد انتهاء المراجعة الحالية، وانتهاء المستخدم من اختبار نسخة Debug، ومناقشة النتائج، ثم صدور توجيه صريح بالبدء.
  • لا يُسمح لهذه الخطة بتعطيل أو حذف أو استبدال أي مرحلة أو وظيفة سابقة في WOLF OFFLINE VIDEO.
  • التطبيق يظل Offline-first؛ لا بحث تلقائي عن محركات فيديو عبر الإنترنت، ولا تنزيل لها، ولا تشغيل لخدمات توليد فيديو سحابية.
  • تظل محركات الإنتاج محلية ومجانية/مفتوحة المصدر وفق التراخيص الفعلية لإصداراتها وتبعياتها، بعد مراجعة قانونية وتقنية قبل الدمج.
قرار أساسي: نضمّن القدرات المطلوبة داخل التطبيق، لكن لا نشغّل جميع المحركات الثقيلة بالتوازي. يختار مركز التنسيق المحرك المناسب لكل مهمة، ويحرر الموارد بعد انتهاء المهمة.

2. توزيع المسؤوليات

3D أساسي

Godot Engine

المحرك الرئيسي للعوالم ثلاثية الأبعاد: البيئات، الشخصيات، المخلوقات، الكاميرا، الحركة، المشاهد والتفاعل المكاني.

رسم واقعي متخصص

Google Filament

الخامات الفيزيائية PBR، الإضاءة والانعكاسات والظلال واللقطات القريبة التي تستفيد من معالجة واقعية متخصصة.

مؤثرات وجسيمات

Cocos Creator / Cocos Engine

المؤثرات ثنائية وثلاثية الأبعاد، الجسيمات، الدخان والغبار والشرر والعناصر المتحركة. يجب تثبيت نسخة runtime المناسبة لأندرويد وفصلها عن متطلبات المحرر.

رسوم برمجية

libGDX

الحركة الرياضية والمؤثرات المخصصة الخفيفة، المعالجة البرمجية ثنائية الأبعاد، وبعض مهام التركيب التي لا تحتاج محرك مشاهد كاملًا.

2D وParallax

KorGE

تحريك طبقات الصور والخلفيات، المشاهد ثنائية الأبعاد، العمق الوهمي والانتقالات المبنية على Kotlin.

هوية وعناوين

Lottie Android

الشعارات والعناوين والبطاقات والانتقالات المتجهة، بما فيها عناصر هوية WOLF CODE S وبصمة الذئب السينمائية.

واجهة معاينة

SceneView

واجهة Android للمعاينة والتعامل مع المشاهد ثلاثية الأبعاد فوق Filament. ليس محرك رسم مستقلًا إضافيًا ولا ينبغي احتساب تكرار محرك Filament.

إعداد خارج التطبيق

Blender

أداة خارجية لإنتاج الأصول: النماذج والشخصيات والهياكل العظمية والتحريك والبيئات والخامات. لا يُضمّن محرر Blender داخل APK.

4. لغة التواصل الموحدة: WOLF Scene Contract

لا يمكن تشغيل كود محرك مباشرة داخل محرك آخر. لذلك تُعرّف أوامر محايدة، ثم يترجم Adapter خاص بكل محرك تلك الأوامر إلى واجهته الأصلية.

5. مسار إنتاج اللقطة الواحدة

  1. يحلل Hub وصف اللقطة ويحوّله إلى مشهد وأهداف بصرية قابلة للتنفيذ.
  2. يختار المحرك الأساسي. مثال: Godot لبناء ممر ثلاثي الأبعاد وتحريك الشخصية والكاميرا.
  3. تُسند المهام المتخصصة فقط: Filament لخامة/إضاءة محددة، Cocos لجسيمات، libGDX لتشويه برمجي، KorGE لطبقات 2D، وLottie للعنوان عند الحاجة.
  4. تُنتج المحركات مخرجات محددة: إطارات، طبقات شفافة، خامات أو بيانات حركة وفق عقد موحد.
  5. تجمع محطة التركيب المخرجات وتوحّد التوقيت واللون والشفافية وترتيب الطبقات.
  6. يمر الناتج إلى خط إنتاج الفيديو الحالي، مع الحفاظ على الصوت والفصول ونقاط الاستكمال والتصدير.
  7. بعد إتمام المهمة، يحرر Hub موارد المحرك والذاكرة والسياقات الرسومية غير اللازمة.
مثال إخراجي: Godot يبني الممر والشخصية وحركة الكاميرا؛ Cocos ينتج الغبار؛ libGDX يضيف تشويشًا محسوبًا؛ Filament يتولى لقطة خامة قريبة عند الحاجة؛ ثم يركّب WOLF الناتج في إطار واحد.

6. قواعد الإخراج والرعب السينمائي

ما لا نراه

الحجب والمساحات الفارغة والظلال المقصودة بدل الكشف الكامل المبكر عن الكيان.

حركة غير طبيعية

حركة دقيقة أو متأخرة أو غير متوافقة مع التوقعات، مع تجنب الحركة العشوائية غير المبررة.

إضاءة تقود العين

توجيه الانتباه بمصادر ضوء محدودة، وتباين محسوب وضباب وظلال متسقة.

إيقاع وصمت

ترك مساحة للترقب، ومزامنة المؤثرات الصوتية مع الحدث بدل ملء كل لحظة بالمؤثرات.

7. الأداء والاستقرار على الهاتف المستهدف

الهاتف المرجعي: Realme 7، Android 12، Helio G95، Mali-G76 MC4. يجب قياس نسخة الجهاز الفعلية والذاكرة المتاحة ودعم الرسوميات على الجهاز قبل تثبيت إعدادات الإنتاج.

  • لا تشغيل متزامن لعدة محركات 3D ثقيلة إلا إذا أثبت القياس ضرورة ذلك وإمكانية تحمله.
  • تفضيل المعالجة المرحلية وإخراج الطبقات/الإطارات ثم تحرير الموارد.
  • معاينة منخفضة التكلفة، مع إعدادات إنتاج منفصلة يمكن رفعها تدريجيًا.
  • إدارة صارمة للذاكرة، أحجام الأصول، دقة الخامات، الجسيمات، والـrender targets.
  • قياس الحرارة والذاكرة ومعدل الإطارات وزمن التصدير واستهلاك البطارية على الهاتف الفعلي.
  • المحاكي لا يثبت أداء Helio G95 أو Mali-G76 ولا يحاكي حرارة الجهاز وسياسات الشركة المصنعة بالكامل.
  • معدل 24 إطارًا في الثانية هدف اختبار لاحق وليس قرارًا نهائيًا؛ يجب قياسه مقابل معدل 12 إطارًا الحالي وجودة الفيديو ووقت التصدير.
لا يُعلن نجاح الأداء أو جودة الفيديو قبل بناء نسخة فعلية واختبارها على الهاتف. لا تكفي اختبارات JVM أو المحاكي لإثبات ذلك.

8. المرونة والبدائل عند الفشل

  • لكل مهمة مسار أساسي ومسار بديل أخف، مع الحفاظ على مدة اللقطة وترتيبها.
  • إذا فشل محرك أو تجاوز حدود الموارد، يعيد Hub المحاولة بإعدادات أقل أو يختار محولًا بديلًا.
  • إذا تعذر إنتاج فيديو متحرك، يستخدم النظام خطة الإطارات المتغيرة والحركة الافتراضية والقص والانتقالات المحلية المعتمدة سابقًا.
  • لا يؤدي فشل مؤثر واحد إلى إيقاف الفيلم كاملًا؛ يسجل النظام سبب الفشل ويواصل عبر البديل المتاح.
  • كل خطوة إنتاج قابلة للاستئناف، ولا يعاد حساب الناتج الصحيح دون داعٍ.

9. الترخيص والحجم والتبعيات

  • يجب التحقق من ترخيص كل إصدار فعلي، وكل إضافة ومكتبة تابعة، ومتطلبات الإشعار وحقوق النشر قبل تضمينها.
  • لا يكفي ترخيص المحرك الأساسي وحده لإثبات أن كل الإضافات والأصول حرة أو مناسبة للتوزيع.
  • يجب قياس زيادة حجم APK/AAB بعد نموذج دمج حقيقي؛ التقديرات الأولية ليست أرقامًا مضمونة.
  • الأصول ثلاثية الأبعاد والخامات والصوت قد تزيد الحجم أكثر من كود بعض المحركات.
  • يُراجع توافق ABI، إصدارات Android، OpenGL ES/Vulkan، حجم المكتبات الأصلية، وتعارضات Gradle/NDK.
  • لا تُضاف خدمات مدفوعة أو اعتماديات شبكية أو تنزيلات محركات تلقائية.

10. مراحل التنفيذ المقترحة بعد المراجعة

  1. تثبيت خط الأساس: استلام ملاحظات Debug والملفات الناتجة، مراجعة العيوب، ثم تحديد نسخة مستقرة لا تتأثر بها المراحل السابقة.
  2. جرد التوافق: فحص الإصدارات والتراخيص وطرق تضمين Android وABI ومتطلبات البناء لكل محرك.
  3. تصميم العقود: اعتماد WOLF Scene Contract وواجهات المحوّلات وخطة الأصول GLB/glTF.
  4. بناء الأساس المركزي: تنفيذ Hub وCode Library وطبقة الموارد والتوقيت والتسجيل والاسترداد.
  5. نماذج إثبات صغيرة: اختبار كل محرك منفردًا داخل التطبيق، ثم اختبار نقل مخرجاته إلى محطة التركيب.
  6. دمج تدريجي: إضافة المحركات واحدًا بعد الآخر مع اختبارات رجعية لكل مرحلة وعدم كسر خط الفيديو الحالي.
  7. مشاهد مرجعية: إنشاء مجموعة لقطات رعب متنوعة تقيس جودة 2D و3D والإضاءة والحركة والمؤثرات.
  8. اختبار الجهاز: قياس الأداء والحرارة والذاكرة والتصدير على Realme 7 الفعلي، وضبط مستويات الجودة والبدائل.
  9. قبول المستخدم: مراجعة النتائج والملفات والمخرجات قبل الانتقال لأي مرحلة لاحقة أو إعداد Release.

11. ما لا يدخل ضمن هذه الخطة

  • لا مولدات فيديو سحابية ولا البحث التلقائي عن محركات فيديو أو تنزيلها.
  • لا تشغيل تلقائي لخدمات أو محركات خارجية على مدار الساعة.
  • لا تضمين محرر Blender داخل التطبيق.
  • لا استبدال محرك الفيديو الحالي قبل إثبات أن البديل يعمل ويجتاز اختبارات التوافق.
  • لا دمج أو تعديل لفرع main أو دمج Pull Request دون موافقة صريحة من المستخدم.
  • لا بدء تنفيذ هذه الخطة قبل اكتمال المراجعة الحالية وتوجيه المستخدم.
