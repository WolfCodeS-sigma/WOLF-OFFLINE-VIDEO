# سياسة تنظيم عمليات WOLF CI والتحقق

## الهدف

حماية عمليات البناء والاختبارات من الإلغاء بسبب وصول Commit جديد، وضمان عدم إعلان نجاح مرحلة قبل اختبار النسخة البرمجية نفسها.

## قاعدة منع الإلغاء

- لا تستخدم `cancel-in-progress: true` في أي Workflow خاص بالبناء أو الاختبار أو التدقيق.
- استخدم `queue: max` مع مجموعة مستقلة لكل Workflow، مرتبطة بمرجع GitHub الحالي.
- لا تضع Workflows مختلفة في مجموعة واحدة؛ يجب أن يكون لكل Workflow اسم مجموعة فريد حتى لا يلغي أو يحجب تشغيلًا مستقلًا.
- يظل لكل مجموعة تشغيل واحد جارٍ، وتنتظر التشغيلات التالية دورها بدل إلغاء التشغيل الجاري. حد GitHub للطابور هو 100 تشغيل منتظر لكل مجموعة؛ عند بلوغ الحد، لا تُرسل Commits إضافية قبل تفريغ الطابور.
- إذا كانت إمكانات الطابور غير متاحة في Workflow معين، نفّذ Commit واحدًا، وانتظر اكتمال تشغيله، وافحص نتيجته قبل Commit التالي.

## تنظيم الوظائف داخل Workflow

- استخدم `needs` عندما تعتمد عملية على نتيجة عملية أخرى؛ لا تبدأ الاختبار التكاملي قبل نجاح البناء أو المتطلبات السابقة.
- شغّل فقط الوظائف المستقلة بالتوازي.
- في Workflow المرحلة 13: يبدأ بناء التطبيق واختبارات الجودة أولًا، ثم اختبار Android 12 للتطبيق؛ ويمكن تنفيذ فحص الأصول وتغليف KorGE بالتوازي مع بناء التطبيق. لا يبدأ اختبار محركات Stage 11 إلا بعد نجاح اختبار Android 12 وفحص الأصول وتغليف KorGE.
- اختبارات المحركات الأربعة داخل مجموعة Stage 11 تنفذ بشكل مستقل ومتتابع، وتسجل نجاح أو فشل كل محرك على حدة. فشل محرك لا يمنع تشغيل بقية المحركات ولا يخفي نتائجها.

## دورة الإصلاح والتحقق

1. افحص سجل الفشل وحدد السبب الجذري والملفات التي تتأثر به.
2. عالج سببًا واحدًا محددًا في Commit مستقل، دون اختصارات أو ملفات ناقصة أو TODO.
3. انتظر نتيجة Workflow التي تحمل SHA الخاص بهذا Commit.
4. افحص كل الوظائف وسجلاتها، لا علامة الحالة العامة فقط.
5. لا تنسب نتيجة تشغيل إلى SHA آخر، ولا تعتبر تشغيلًا ملغى أو متجاوزًا نجاحًا.
6. بعد اجتياز الاختبارات، انتقل إلى الإصلاح التالي. إذا فشل اختبار، ارجع إلى سجله وأصلح السبب الجديد قبل إضافة إصلاحات غير مرتبطة.

## التعامل مع إيقاف المحادثة أو انقطاع الاتصال

إيقاف واجهة المحادثة أو اختيار «تخطي» لا يحذف Commit ولا يوقف GitHub Actions تلقائيًا. حالة العمل المرجعية هي Commit SHA وحالة Workflow داخل GitHub. عند استئناف المراجعة، يجب جلب حالة التشغيل والـSHA من GitHub قبل اتخاذ أي إجراء جديد.

## النطاق والحماية

- لا تُدمج Pull Requests ولا تعدل `main` دون موافقة صريحة.
- لا ترفع APK أو تنشر Artifacts إلا بطلب صريح.
- لا تغير بيانات المشاريع أو ملفات المستخدم أو الأصول الإنتاجية عند إصلاح مشاكل CI.
- تظل المحركات المعزولة اختبارات توافق فقط؛ لا يعني نجاحها دمجها في مسار الإنتاج.
