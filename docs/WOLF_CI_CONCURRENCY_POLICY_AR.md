# سياسة تنظيم عمليات WOLF CI والتحقق

## الهدف

حماية كل تشغيل بناء أو اختبار من الإلغاء بسبب وصول Commit جديد، ومنع تضارب Gradle/Maven بين Workflows والفروع المختلفة، وإثبات نتيجة كل Commit على SHA نفسه قبل الانتقال إلى الإصلاح التالي.

## قفل البناء المشترك ومنع الإلغاء

- تستخدم جميع Workflows التي تشغل Gradle أو Android Emulator مجموعة concurrency واحدة حرفيًا: `wolf-gradle-regression-global`.
- يجب أن تكون إعدادات المجموعة `queue: max` وألا يُستخدم `cancel-in-progress: true` معها.
- توحيد اسم المجموعة عبر Workflows والفروع يجعل تشغيلات البناء والاختبارات تنتظر بعضها في طابور واحد بدل تشغيل Gradle/Maven بالتوازي أو إلغاء تشغيل سابق.
- تسمح GitHub Actions بتشغيل واحد نشط وما يصل إلى 100 تشغيل منتظر في مجموعة `queue: max`. هذا حد للطابور وليس ضمانًا لطابور غير محدود؛ لا تُرسل تشغيلات إضافية عندما يصل الطابور إلى الحد، وانتظر إفراغه.
- فحوص `asset-intake` التي تشغّل Python فقط ولا تستخدم Gradle أو المحاكي يمكن أن تبقى في مجموعة مستقلة؛ لا تُشغّلها بالتوازي مع عملية تستهلك موردًا مشتركًا إذا ثبت وجود تعارض.
- يجب أن تستخدم كل Workflows الجديدة الخاصة بالبناء أو Android Emulator اسم المجموعة المشترك نفسه، لا اسمًا خاصًا بالفرع أو Workflow.

## ترتيب الوظائف داخل التشغيل

- بناء التطبيق وLint واختبارات JVM يسبق اختبار تكامل التطبيق على Android 12.
- اختبار تكامل Android 12 يسبق تغليف KorGE في مسار Stage 13؛ يمنع تشغيل مهمتي Gradle ثقيلتين بالتوازي.
- يمكن لفحوص Asset Intake المعتمدة على Python أن تعمل بالتوازي مع بناء التطبيق.
- لا يبدأ اختبار محركات Stage 11 إلا بعد نجاح تكامل Android 12 وتغليف KorGE وفحوص Asset Intake.
- تنفّذ اختبارات Godot وFilament وlibGDX وLottie واحدة تلو الأخرى، مع تسجيل نتيجة مستقلة لكل محرك وجمع سجلات التشخيص حتى إذا فشل محرك واحد. لا يُخفى فشل أي محرك ولا يُعلن نجاح المجموعة إلا إذا نجحت الأربعة.
- تشغيلات PR من مستودعات خارجية تستخدم كاش Gradle للقراءة فقط؛ تشغيلات المستودع نفسه يمكنها حفظ واستعادة الكاش. لا تسمح لفرع خارجي بكتابة كاش مشترك.

## دورة الإصلاح والتحقق

1. افحص سجل الفشل وحدد السبب الجذري والملفات والاختبارات المتأثرة.
2. عالج سببًا واحدًا محددًا في Commit مستقل؛ لا تجمع إصلاحات غير مترابطة.
3. انتظر انتهاء Workflow الذي يحمل SHA هذا الـCommit.
4. افحص كل Job وسجلاته، لا الحالة العامة فقط.
5. لا تنسب نتيجة تشغيل إلى SHA آخر، ولا تعتبر تشغيلًا ملغى أو متجاوزًا نجاحًا.
6. إذا فشل الاختبار، عالج السبب الجديد في Commit مستقل ثم أعد دورة التحقق.
7. لا تدفع أكثر من Commit واحد أثناء وجود تشغيل سابق غير مكتمل. وإذا وصل طابور GitHub إلى 100 تشغيل منتظر، أوقف إرسال التشغيلات حتى يفرغ الطابور.

## تهيئة بيئة Android Emulator

- استخدم Runner من Linux x86_64 عند توفر KVM، وتحقق من وجود `/dev/kvm` وصلاحيات القراءة والكتابة قبل تشغيل المحاكي.
- ثبت API level وTarget وABI وملف الجهاز وRAM والأنوية ومهلة الإقلاع صراحةً؛ لا تترك الاختيار الافتراضي للمحاكي.
- إعداد Stage 13 المجتاز: Android 12 / API 31 / Google APIs / x86_64 / Pixel 2 / 4 cores / 4096 MB RAM / 512 MB heap، مع KVM و`-gpu software` وتعطيل snapshots والصوت والرسوم المتحركة. لا تستبدل Renderer دون اختبار rendered-frame.
- اجمع ADB وlogcat ونتائج instrumentation عند الفشل، وميّز بين تعطل المحاكي وفشل assertion في التطبيق.

## التعامل مع انقطاع المحادثة أو توقفها

GitHub هو سجل الحالة الدائم. إغلاق المحادثة أو الضغط على «تخطي» لا يثبت اكتمال العملية ولا يعني إلغاء Commit أو Workflow. عند الاستئناف، اجلب SHA الحالي، والـPR المفتوح، وكل Jobs وحالاتها، ثم تابع أول إصلاح غير مكتمل. لا تعِد تشغيل نجاح سابق ولا تدفع Commit جديدًا أثناء تشغيل غير مكتمل.

**أمر استئناف قابل للنسخ عند انقطاع المحادثة:**

```text
استأنف العمل على مستودع WOLF-OFFLINE-VIDEO من الحالة الفعلية في GitHub. اقرأ سياسة docs/WOLF_CI_CONCURRENCY_POLICY_AR.md، واجلب آخر Commit SHA والـPR المفتوح وحالة كل Actions runs/jobs المرتبطة بالمراحل 1–13. لا تعِد تشغيل عملية ناجحة ولا تنشئ Commit جديدًا قبل التأكد من انتهاء التشغيل السابق. تابع من أول إصلاح غير مكتمل، إصلاح واحد في كل Commit، وانتظر نتيجة اختباره وافحص سجلات كل Job. لا تعدّل main ولا تدمج أي PR دون إذني. لا تبدأ مرحلة جديدة قبل اجتياز اختبارات المراحل السابقة.
```

## النطاق والحماية

- لا تُدمج Pull Requests ولا تعدّل `main` دون موافقة صريحة.
- لا ترفع APK أو تنشر Artifacts إلا بطلب صريح.
- لا تغيّر بيانات المشاريع أو الملفات أو الأصول الإنتاجية عند إصلاح مشاكل CI.
- تظل المحركات المعزولة اختبارات توافق فقط؛ لا يعني نجاحها دمجها في مسار الإنتاج.
- لا يُعلن اكتمال مرحلة أو جاهزية المرحلة التالية لمجرد نجاح CI؛ يجب إغلاق نطاق المرحلة نفسه ومراجعة القيود والاختبارات الواقعية المطلوبة.
