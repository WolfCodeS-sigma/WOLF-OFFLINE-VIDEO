الخطة الهندسية الرئيسية المحدّثة

منظومة طبقية تجمع التوليد الإجرائي بالأصول السينمائية الواقعية، ثم تربطهما بالمحركات عبر WOLF Motion Hub، وتنتهي بخط إخراج MP4 موحّد.

مرجع تشغيل — الإذن الحالي للخطوة الأولى فقط؛ كل خطوة تالية تحتاج توجيه المستخدم

1. القرارات الحاكمة

  • المستودع الوحيد: WolfCodeS-sigma/WOLF-OFFLINE-VIDEO.
  • الإنتاج Offline؛ لا بحث أو تنزيل أو تشغيل مولدات فيديو سحابية.
  • في مسار الصور، المستخدم هو من يختار ويرفع الصور. التطبيق يحللها ويفصل طبقاتها ويحرك العناصر المناسبة، ولا يختار صورًا بدلًا عنه.
  • مسار مستقل للموشن الهجين 3D/2.5D دون صور يرفعها المستخدم، يعتمد على الأصول المحلية والمولدات البرمجية.
  • مكتبة الأصول جزء من توزيع التطبيق نفسه، بلا ملف منفصل يطلب من المستخدم استيراده ولا تنزيل وقت التشغيل.
  • تشفير البيانات المحلية مؤجل. توقيع Release وتجهيز APK مؤجلان إلى بوابة الإصدار.
  • المستخدم وحده يحدد بدء المراحل؛ هذه الخطة لا تعني بدء التنفيذ. لا دمج أو تعديل main دون موافقته.

2. التشخيص المرجعي لفيديوهات Debug

هاتف الصحراء الزراعية

مسار بلا صور رفعها المستخدم، لكن المخرجات كانت مربعات ودوائر ومثلثات وألوانًا بدل بيئة سينمائية، مع شريط أحمر أعلى الفيديو وصوت مؤثرات منخفض. المطلوب أصول/بيئات محلية وتوليد إجرائي مقبول، ومنع UI overlay من دخول الفيديو.

صوفيا

الصور الـ32–34 اختارها المستخدم. العيب في تحليل الصور المختارة وفصل طبقاتها وتحديد ما يتحرك وفق المشهد، وفي حركة كاميرا عامة شوّهت الصور وظهور أشكال هندسية كأشباح. يجب حفظ الصورة الأصلية؛ وعند فشل الفصل تُستخدم حركة آمنة على الصورة كاملة، لا صورة بديلة ولا جسم هندسي.

الجاثوم

اختار المستخدم 11 صورة و30 ثانية وسجل تعليقًا مدته نحو 7 ثوانٍ. ملف MP4 المرفوع قيس بنحو 7.012 ثانية. يجب تتبع السبب في جدول اللقطات والإطارات وPTS ونهاية مساري الصوت والفيديو؛ المدة المختارة هي المرجع ولا ينتهي الفيديو مع تعليق أقصر.

3. المواصفات السينمائية الملزمة

لا أجسام هندسية بديلة

لا دوائر/مثلثات/مربعات بدائية كشخصيات أو أشباح. البديل المقبول: أصل سينمائي، silhouette مقصود، لقطة بديلة، أو الصورة الأصلية.

الشخصيات والبيئات

أجسام وخامات وإضاءة وظلال وRigging وتحريكات واقعية. المحرك وحده لا يولد بشرًا واقعيين من primitives.

الشريط الأحمر

فصل شريط تقدم الواجهة عن Render Target ومنع ظهوره في MP4.

العلامة المائية

شعار WOLF شبه شفاف بملمس دم سائل وقطرات متدلية، في موضع آمن لا يحجب الحدث.

الخط الدموي

كل النصوص والعناوين والتوضيحات داخل الفيلم بالهوية الدموية نفسها مع Arabic shaping وRTL وقراءة واضحة. واجهة التطبيق بخط عربي واضح عادي.

الصوت

مسارات منفصلة للراوي والجو والمؤثرات والموسيقى، مع LUFS/True Peak وCompressor وDucking وLimiter ومنع clipping.

سلامة الصور

حفظ الأصل والنسبة؛ لا تمديد أو تشويه للوجه أو الجسم. عند فشل الفصل، حركة محدودة وآمنة على الصورة كاملة.

المدة

targetDuration يحكم الإطارات والتصدير؛ تعليق 7 ثوانٍ لا ينهي فيلمًا اختيرت مدته 30 ثانية. لا قص تلقائي لتعليق أطول.

كل المحركات تبقى ضمن التصميم المطلوب، لكن إدخال Runtime كل واحد إلى APK يمر باختبار Android/ABI/NDK/Gradle/Graphics API والحجم والذاكرة. إذا تعذر الدمج المستقر، يتوقف هذا الجزء للمراجعة ولا يُفرض على حساب استقرار التطبيق.

  • لا تشغيل لجميع المحركات الثقيلة بالتوازي؛ تحميل عند الحاجة وتحرير الموارد بعدها.
  • البداية بتبادل إطارات/طبقات عبر مسار محدود الذاكرة وآمن. مشاركة GPU textures بين سياقات مختلفة تحسين لاحق فقط بعد إثباته.
  • Godot يدعم تضمين Android عبر AAR والتواصل ثنائي الاتجاه، لكن وثائقه تنبه إلى أن نسخة واحدة فقط من المحرك مدعومة في Android process، ويجب إدارة lifecycle/التدوير بعناية.

7. المكتبة داخل التطبيق والحجم

المستخدم لا يريد ملف مكتبة منفصلًا ولا استيرادًا يدويًا. المرجع هو أن تكون الأصول المعتمدة جزءًا من إصدار التطبيق، وتعمل دون اتصال بعد التثبيت.

  • في توزيع APK مباشر: تضمين الأصول المختارة داخل APK كـassets مع manifest مدمج.
  • إذا احتاج Runtime لمسارات ملفات، يستخرج التطبيق ما يلزم تلقائيًا إلى مساحة التطبيق الخاصة؛ هذا استخراج محلي داخلي لا حزمة مرافقة.
  • لا تنزيل شبكي ولا on-demand assets في المسار الأساسي.
  • يجب حساب مساحة التثبيت والنسخ المؤقتة والتحديث؛ لا نفترض أن حجم APK يساوي المساحة التي يحتاجها التثبيت دائمًا.
  • التقدير السابق 2–4 GB للحزمة الأولية مُلغى كهدف ثابت. نحدد الحجم من manifest حقيقي بعد الجرد والضغط والبناء.
  • تستخدم LOD وإعادة استخدام الخامات وضغطًا مناسبًا مثل KTX2 عندما يتوافق مع المحرك والجهاز، دون تدهور الواقعية.
  • Play Asset Delivery install-time جزء من APK set عند التثبيت ومتاح عند إطلاق التطبيق، لكنه ليس APK واحدًا ويتطلب قناة توزيع Play؛ لذلك ليس اختيارنا الافتراضي. لا نغيّر توزيع APK المباشر دون موافقة المستخدم.

9. واجهة المستخدم والصوت

  • شاشة رئيسية بالهوية المعتمدة، Offline indicator، إنشاء مشروع، المشاريع الأخيرة، المكتبة والإعدادات.
  • شاشة اختيار المسار ببطاقات مستقلة، خاصة فصل مسار الهجين بلا صور عن مسار صور المستخدم.
  • مساحة عمل لكل مشروع ومحطات: القصة، المشاهد، الصورة والحركة، الصوت، الإخراج.
  • استوديو الصوت يعرض Teleprompter للنص كاملًا أثناء التسجيل، يميز السطر الحالي، تمرير يدوي/تلقائي، تكبير وتصغير الخط، المسافات والسرعة، مؤقت وموجة صوتية وإيقاف واستكمال وحفظ أجزاء.
  • الخط الدموي داخل الفيديو فقط؛ واجهة التطبيق بخط عربي واضح.
  • الواجهة RTL، ألوان فحمية وقرمزية محدودة، أيقونات واضحة وأزرار كبيرة؛ تُقارن لقطات حقيقية بالمرجع على Realme 7.

10. الترتيب التنفيذي الأفضل

ترتيب تبعيات هندسي مقترح، لا يبدأ تلقائيًا. كل بوابة تتطلب مراجعة ونجاح الاختبار قبل التالية.

  1. إغلاق مراجعة Debug وجمع الأدلة: ربط كل عيب بملف/توقيت/إطار.
  2. تدقيق خط الإنتاج دون تغيير: رسم مسار القصة والمشاهد والصور والصوت والتصدير وتحديد مصادر الحقيقة.
  3. إصلاح المدة والتوقيت والتصدير: targetDuration وPTS وعدد الإطارات ونهاية muxer؛ اختبار 30 ثانية مع تعليق 7 ثوانٍ.
  4. تنظيف الرندر والـFallback: منع الشريط الأحمر والأجسام الهندسية البديلة.
  5. تحسين Storyboard Planner: ربط كل حدث بلقطة ومكان وشخصية وتوقيت واستمرارية.
  6. سياسة جودة وترخيص الأصول: معايير قبول ورفض وبيانات مصدر وتوافق.
  7. جرد WOLF Cinematic Asset Library: تثبيت خط الأساس وإعداد مصفوفة بكل فئات الأصول المطلوبة والموجود والمفقود؛ الجرد لا يعني أن المكتبة قد تم توريدها.
  8. بناء Asset Registry & Quality Gate: إنشاء الفهرس وسير الاستلام والفحص والترخيص والقبول/الرفض، ثم بدء إدخال الأصول الفعلية بعد جاهزية البوابة.
  9. تصميم WOLF Procedural Generation Library: مولدات الهندسة والمواد والبيئات والمؤثرات وحدودها.
  10. اختبار تعاون المولدات والأصول: تخصيص قوالب واقعية مع حفظ الأصل والترخيص.
  11. POC منفرد لكل محرك: اختبار Runtime وABI/NDK/Gradle/Graphics API والحجم والذاكرة.
  12. اعتماد أدوار المحركات: تثبيت الدور الفريد لكل مكوّن وتوثيق أي تعارض قبل الدمج.
  13. بناء Motion Code Library وScene Contract: الأوامر المشتركة والمحوّلات.
  14. بناء WOLF Motion Hub: الجدولة والذاكرة والاختيار والبدائل والاسترداد.
  15. دمج المحركات تدريجيًا: Godot ثم Filament/SceneView ثم Cocos ثم libGDX ثم KorGE ثم Lottie، مع اختبارات رجعية بعد كل دمج.
  16. استكمال مسار صور المستخدم: segmentation والأقنعة والحركة الآمنة وحفظ الأصل وعدم التشويه.
  17. تطوير الهوية الدموية: الخط العربي لكل نصوص الفيديو والعلامة المائية شبه الشفافة.
  18. WOLF Audio Mastering: فصل المسارات والضغط وDucking وLimiter والقياس والمزامنة.
  19. إعادة تصميم الواجهة كاملة: مطابقة المرجع مع ربط الوظائف والملقّن واختبار RTL.
  20. اختبارات القصص المرجعية: هاتف الصحراء (بدون صور)، صوفيا (صور المستخدم)، الجاثوم (11 صورة/30 ثانية/تعليق 7 ثوانٍ).
  21. اختبار Realme 7: محاكي قريب ثم الجهاز الفعلي للحرارة والذاكرة والبطارية والتصدير.
  22. Release APK والتوقيع: مفتاح محفوظ خارج المستودع وبناء بعد الموافقة.
  23. التسليم والتوثيق: APK وأدلة الاختبارات والقيود.

11. برنامج استكمال WOLF Cinematic Asset Library بالكامل

شرط الاكتمال: لا تُعلن المكتبة مكتملة إلا بعد توفير واعتماد ودمج واختبار جميع الأصول الإلزامية التي تتطلبها وظائف التطبيق ومساراته والقصص المرجعية والمحركات التي اجتازت اختبارات التوافق. المقصود اكتمال نطاق المشروع، لا جمع كل أصل موجود في العالم أو إضافة محتوى لا يحتاجه التطبيق.

  1. مصفوفة الاحتياج: ربط كل قصة ومسار ومشهد/نوع لقطة ووظيفة بفئة الأصل والأنواع والتنوعات المطلوبة والحركة والخامات والدقة والمحرك المستهدف. تشمل حسب الحاجة الشخصيات البشرية والوجوه والشعر والملابس والمخلوقات والبيئات الداخلية والخارجية والـProps ومجموعات PBR وHDRI والإضاءة والـRigs والحركات والمؤثرات والخطوط والشعارات والصوتيات التي تدخل نطاق المكتبة.
  2. التبعيات والتغطية: تحديد استخدام كل أصل وإعادة الاستخدام والبدائل المقبولة والتنوع اللازم. وجود ملف واحد غير مناسب لا يعني تغطية الفئة.
  3. الترخيص والمصدر: توثيق المصدر والرخصة والإصدار وحقوق الاستخدام والتعديل وإعادة التوزيع والتضمين التجاري عند انطباقه، مع حفظ الأدلة والبصمات. أي غموض يضع الأصل في الحجر ولا يسمح بقبوله.
  4. الفحص السينمائي والفني: معاينة كل أصل وفحص الواقعية والتشريح والخامات وPBR والـRig والـSkinning والتحريك والمقاييس والتبعيات والتوافق والأداء. تُرفض الأصول الكرتونية أو المضحكة أو منخفضة الجودة؛ ولا تُستخدم primitives كبشر أو أشباح.
  5. سد الفجوات: توفير بديل مرخص أو إنشاء أصل مناسب عندما يكون ذلك ممكنًا. إذا تعذر توفير أصل واقعي لفئة إلزامية، يظل ذلك عائقًا معلنًا ولا يُخفى ببديل بدائي.
  6. التضمين Offline: تضمين كل الأصول المقبولة وتبعياتها في التطبيق نفسه مع manifest وإصدارات وبصمات، واختبارها دون اتصال. الاستخراج إلى مساحة التطبيق يكون تلقائيًا داخليًا فقط.
  7. مقياس الإغلاق: تغطية 100% من المتطلبات الإلزامية بحالة APPROVED، وصفر MISSING/UNKNOWN/PENDING/QUARANTINED/REJECTED ضمن المتطلبات الإلزامية، وصفر تبعيات مفقودة، ونجاح اختبارات الاستخدام في القصص المرجعية. تُفصل العناصر الاختيارية عن النسبة.
  8. الاستكمال المرحلي: يستمر إدخال الأصول على دفعات خلال المراحل 09–20 بالتوازي مع المولدات وPOC المحركات والدمج ومسار الصور والهوية والصوت. لا تُغلق البوابة قبل اختبارات المرحلة 20، وتُثبت النسخة النهائية والحجم والتبعيات قبل الإصدار في المرحلتين 21–22.

قاعدة التوقف: أي نقص أو ترخيص غير كافٍ أو فشل جودة أو توافق أو تبعية مفقودة يعيد الفئة للاستكمال؛ لا إعلان اكتمال ولا اعتماد إصدار على مكتبة ناقصة.

15. سياسة التشغيل الجديدة — التطوير المتتابع والدمج والتحقق

هذه السياسة مكمّلة للمراحل الثلاث والعشرين أعلاه، ولا تستبدل ترتيبها أو مواصفاتها أو قرارات المنتج أو حدود المحركات والأصول. تطبق على كل عمل قادم، كما تُستخدم عند إعادة تنظيم الفروع القديمة. لا تمنح هذه السياسة إذنًا تلقائيًا ببدء مرحلة جديدة أو دمج طلب؛ المستخدم يحدد الخطوة التالية ويعتمد الدمج.

15.1 خط التكامل الوحيد

  • يكون فرع main هو خط التكامل التراكمي والمرجع المستقر. بعد استعادة تسلسل المراحل القديمة ودمجها بأمان، يجب أن يحتوي main على كل مرحلة مكتملة ومعتمدة.
  • لا يبدأ تنفيذ مرحلة تطبيقية جديدة قبل إغلاق المرحلة السابقة ودمجها في main واجتياز اختبارات ما بعد الدمج على Commit main الجديد.
  • تبدأ كل مرحلة مستقبلية بفرع جديد من أحدث Commit ناجح في main. لا يُنشأ الفرع من نسخة قديمة أو فرع تجريبي غير معتمد.
  • يكون PR الخاص بالمرحلة موجّهًا إلى main مباشرة. لا تُنشأ طلبات تراكمية متعددة لنفس التغييرات على قواعد قديمة.
  • التطوير المتوازي لمراحل تعتمد إحداها على الأخرى غير مسموح به افتراضيًا. أي استثناء يحتاج توجيهًا صريحًا وخطة تبين قاعدة كل فرع وطريقة إدخاله في main.
  • إذا اضطررنا مؤقتًا إلى فرع متراكم قبل دمج أبيه، فيستهدف PR الابن رأس فرع الأب مباشرة. وبعد دمج الأب في main تُحدّث قاعدة الابن إلى main ويعاد تشغيل كامل بوابة الاختبارات.
  • يُفضّل الدمج بنمط Merge Commit للحفاظ على نسب الـCommits وتسلسلها. لا يُستخدم Squash أو إعادة كتابة التاريخ في مسار الاستعادة دون قرار موثق يحفظ التتبع والتغييرات.
  • لا حذف أو إعادة تسمية أو إعادة ضبط للفروع القديمة قبل اكتمال جردها وتحديد مصير كل Commit. الفروع المجمدة تحفظ كمرجع تاريخي.

15.2 دورة المرحلة الإلزامية

  1. تثبيت نطاق المرحلة ومتطلباتها وتحديد الميزات السابقة التي يمكن أن تتأثر.
  2. إنشاء فرع المرحلة من أحدث main ناجح وتسجيل SHA نقطة البداية.
  3. تنفيذ التغيير مع الحفاظ على السلوك والبيانات والواجهات السابقة. كل ملف مصدر يُنشأ أو يُستبدل يُكتب كاملًا من أول سطر إلى آخر سطر.
  4. مراجعة كل الملفات المتغيرة ومقارنة Diff مع قاعدة المرحلة، بما فيها Gradle وManifest وAssets وWorkflows والاختبارات والتوثيق.
  5. إضافة اختبارات للسلوك الطبيعي والحدود والمدخلات غير الصالحة وفشل الاعتماد والاسترداد وعدم التأثير على الميزات السابقة.
  6. إنشاء PR واحد للمرحلة، وقاعدته main بعد استعادة خط الدمج. يوثق PR الـSHA الأساس والـSHA المختبَر ونطاق التغيير والاختبارات.
  7. تشغيل بوابة CI على نتيجة دمج PR مع قاعدة main الحالية، وليس على Commit قديم أو تشغيل تابع لفرع آخر.
  8. عند نجاح جميع الفحوص، تُعرض النتيجة للمستخدم لاعتماد الدمج. لا يُنفذ الدمج دون توجيهه الصريح.
  9. بعد الدمج، يُشغّل اختبار Post-Merge على Commit main الناتج. لا تبدأ المرحلة التالية إلا بعد نجاحه.
  10. إذا فشل أي فحص، تتوقف المرحلة عند موضع الفشل، ويُشخّص السبب الجذري ثم تعاد الاختبارات المتأثرة والكاملة المطلوبة على SHA جديد.

15.3 بوابة البناء والاختبار الموحدة

فحوص البناء الثابتة:

  • بناء Debug APK من بيئة نظيفة، وتشغيل Android Lint وجميع اختبارات JVM.
  • التحقق من ملفات APK الناتجة والمكتبات الأصلية المطلوبة لكل ABI، وعدم إدخال ملفات اختبار أو أصول غير معتمدة في إصدار الإنتاج.
  • تشغيل اختبارات أدوات الأصول والفهارس والتراخيص والبصمات عند وجودها في نطاق التغيير، مع إبقاء اعتماد الأصول Fail-Closed.
  • فحص تغييرات Gradle وVersion Catalog وGradle Wrapper وgradle.properties وManifest وملفات CI ضمن Diff.

فحوص Android والتكامل:

  • تشغيل اختبارات Android Instrumentation على Android 12/API 31 للمسارات المدعومة.
  • الحفاظ على اختبارات الصوت والفيديو وMP4 وMediaStore والمشروعات والحفظ والاستعادة وCheckpoints والأصول والصور والـFallback.
  • التحقق من مدة الإخراج وعدد الإطارات وPTS ومزامنة الصوت وفحص ملف MP4 فعليًا، لا الاكتفاء بنجاح تجميع APK.
  • اختبار الصلاحيات والحفظ والتعامل مع ملفات المستخدم كلما مسّ التغيير هذه المسارات.
  • إذا لم توجد ميزة Regression مناسبة لسلوك سابق يتأثر بالتغيير، يضاف اختبار قبل اعتماد الدمج؛ غياب الاختبار لا يُفسر على أنه نجاح.

فحوص المحركات المعزولة:

  • تبقى تجارب المحركات منفصلة عن التطبيق الإنتاجي حتى اعتماد دورها ومرحلة دمجها.
  • عند تعديل عقد مشترك أو Adapter أو إعداد بناء للمحركات، تُشغّل الاختبارات المتأثرة، وتُشغّل مجموعة التوافق الكاملة عند بوابة التكامل الشاملة.
  • تشمل المصفوفة الحالية Godot وFilament وlibGDX وLottie، وتغليف KorGE، والتحقق من SceneView بوصفه واجهة مبنية على Filament لا محركًا مستقلًا.
  • يظل Cocos BLOCKED — NOT PASSED حتى يتوفر مشروع Android أصلي مولّد من Creator 3.8.7 وإثبات إطار مرسوم فعلي. لا يدخل APK الإنتاجي قبل ذلك.
  • نجاح POC منفرد لا يعني اعتماد المحرك إنتاجيًا؛ يلزم اختبار Adapter والتوقيت والمخرجات والذاكرة والاسترداد والتكامل مع خط MP4 في مرحلته المقررة.
  • يظل اختبار Realme 7 الفعلي بوابة المرحلة 21، ولا يُستبدل بالمحاكي.

15.4 قواعد GitHub Actions والبناء القابل لإعادة الإنتاج

  • تُشغّل اختبارات PR على pull_request المستهدف إلى main، وفحوص Post-Merge على push إلى main. التشغيل اليدوي لا يستبدل فحص PR المطلوب.
  • لا تُستخدم cancel-in-progress: true في مجموعات Gradle/Android المشتركة. تُصفّ التشغيلات باستخدام queue: max أو سياسة انتظار مكافئة تمنع إلغاء تشغيل مطلوب.
  • حالات cancelled وskipped وtimed_out وغياب Status Check أو عدم بدء Workflow تعني أن البوابة غير مكتملة، ولا تُحسب نجاحًا.
  • يُربط كل تقرير CI بالـCommit SHA الدقيق الذي اختُبر. لا تُنقل نتيجة خضراء من SHA أقدم إلى SHA أحدث.
  • تُثبت إصدارات JDK وGradle وAndroid SDK وBuild Tools وNDK وCMake لكل وحدة. يظل JDK 17 وGradle 8.13 وإعداد SDK الخاص بالتطبيق كما هو حتى يثبت احتياج موثق لتغييره، وتبقى متطلبات المحركات المعزولة منفصلة ومثبتة.
  • يجب حل الاعتمادات من بيئة نظيفة. تُستخدم المرايا الموثوقة وخطة استعادة للمصادر الخارجية، ويُسجل HTTP 429 أو فشل المصدر على أنه فشل بنية تحتية لا فشل منطق التطبيق.
  • الكاش وسيلة تسريع فقط، وليس شرطًا لصحة البناء. يجب نجاح بناء نظيف لا يعتمد على Cache سابق.
  • لا تُخفى أعطال البنية التحتية بإعادات غير محدودة. يسمح بإعادة محدودة عند ثبوت عطل خارجي عابر مع الاحتفاظ بسجل المحاولة الأولى.
  • عند فشل محاكي أو Instrumentation، تجمع سجلات AndroidRuntime وLogcat ونتائج XML وتقارير Gradle وبيانات المحاكي قبل تصنيف السبب. رسالة exit code 1 وحدها ليست تشخيصًا جذريًا.

15.5 معيار مراجعة الكود والملفات

  • تُراجع الملفات كاملة من أول سطر إلى آخر سطر، لا موضع Diff فقط، عندما يمس التغيير دورة حياة أو إعدادًا أو عقدًا مشتركًا.
  • كل ملف يُنشأ أو يُستبدل يُسلّم كاملًا دون اختصار أو علامات حذف مثل ... أو عبارة «بقية الملف كما هي».
  • يمنع إدخال TODO أو FIXME أو Placeholder أو كود تجريبي غير مكتمل في الملفات التي تُقدم على أنها منجزة. الوظيفة غير المنفذة توثق كقيد صريح خارج الكود.
  • لا يُحذف كود قائم أو يُستبدل مسار إنتاج أو مخطط بيانات لتبسيط التنفيذ. يتطلب التغيير توافقًا خلفيًا واختبار ترحيل/قراءة للبيانات القديمة عند الحاجة.
  • تشمل المراجعة أثر التغيير على Offline-first والصور والصوت ومدة الفيلم وPTS وMP4 والمشروعات والصلاحيات والحفظ والاستعادة والذاكرة والأصول والمحركات ذات الصلة.
  • نجاح الاختبارات المحدودة يثبت نطاقها فقط. لا توصف المرحلة بأنها سليمة بالكامل دون اجتياز بوابة التكامل المقررة.

15.6 حماية main والتحكم في التقدم

  • يمنع Push المباشر إلى main في مسار العمل المعتاد، وتُطلب PRs مع Required Status Checks لجميع الفحوص الإلزامية.
  • يمنع Force Push أو إعادة كتابة تاريخ main. لا يُدمج PR إذا كانت قاعدته قديمة أو ظهرت تعارضات غير محلولة أو فحوص ناقصة.
  • الدمج يحتاج نجاح جميع الفحوص واعتماد المستخدم. بعد الدمج يجب نجاح Post-Merge على Commit main.
  • لا تبدأ المرحلة التالية تلقائيًا بعد اكتمال الحالية. يتوقف التنفيذ ويُرسل تقرير بالنتيجة والخطوة التالية ثم ينتظر توجيه المستخدم.
  • لا تتغير المراحل الثلاث والعشرون ولا قرارات المنتج السابقة بسبب هذه السياسة. أي تغيير في النطاق أو الترتيب يحتاج اعتمادًا منفصلًا.
