# المرحلة 13 — بناء WOLF Motion Code Library وWOLF Scene Contract

**الحالة:** إصلاح شامل لمخرجات مراجعة المرحلة 13  
**إصدار المكتبة:** 1.2.0  
**إصدار العقد:** 1.2.0  
**النطاق:** مكتبة رياضية وعقد بيانات محايدان عن المحرك، مع اختبارات JVM. لا دمج محركات ولا تغيير لمسار إنتاج الفيديو.

## 1. تصحيحات Motion Code Library

- استبدال `BigInteger.longValueExact()` بتحقق صريح من النطاق ثم `toLong()`؛ لتجنب استدعاء واجهة غير متاحة على بعض إصدارات Android المدعومة.
- التحقق من تجاوز حساب PTS لنطاق `Long` وإرجاع رفض واضح.
- إضافة `WolfQuaternionCurve` لاستيفاء اتجاهات الدوران على أقصر مسار باستخدام SLERP.
- جعل قوائم مفاتيح المنحنيات نسخًا غير قابلة للتعديل بعد الإنشاء، مع فحص حد 256 مفتاحًا قبل إنشاء النسخة الدفاعية.
- أخذ عينات Vector3 مباشرة من مفاتيح المنحنى باستخدام بحث ثنائي واحد للمحاور الثلاثة، دون إنشاء منحنيات Scalar وقوائم مؤقتة لكل إطار.
- رفض نتائج عددية غير منتهية في عمليات الاستيفاء والتطبيع والتحويل.

## 2. استكمال أوامر الحركة في Scene Contract

أصبح طلب المشهد يدعم:
- منحنيات انتقال `Vector3` للطبقات.
- منحنيات دوران `Quaternion`.
- منحنيات تحجيم `Vector3`.
- منحنيات شفافية `Scalar` ضمن المجال 0..1؛ وتُعامل قيمة المنحنى كمعامل ضرب للشفافية الأساسية للطبقة: `effectiveOpacity = opacityPermille × animatedOpacity`.
- مسارات حركة كاميرا متزامنة للموضع والهدف والمتجه العلوي ومجال الرؤية. يجب أن يحتوي الطلب على مصدر كاميرا واحد فقط: أمر كاميرا ثابت أو مسار كاميرا متحرك، وليس كليهما أو لا شيء.
- التحقق من توافق مواضع المفاتيح داخل المسار، وصلاحية اتجاه الكاميرا عند كل إطار مطلوب.
- يسمح التحجيم السالب بعكس/مرآة الطبقة، لكن يجب أن يحتفظ كل محور بإشارته عبر مفاتيح المسار؛ ويُرفض الصفر أو تغيير الإشارة الذي يعبر بمقياس المحور عبر الصفر.

جميع المنحنيات مطبّعة على المجال 0..1 نسبةً إلى نطاق الإطارات المحدد في الطلب. هذه أوامر بيانات فقط؛ لا تمنح المحول سلطة تغيير مدة الفيلم أو عدد الإطارات أو PTS أو خطة اللقطات.

## 3. حدود الموارد

أُضيفت حدود بروتوكول عامة تمنع الطلبات المفرطة قبل أي تنفيذ:

| البند | الحد الأعلى |
|---|---:|
| البعد الواحد للوحة | 4096 بكسل |
| إجمالي بكسلات اللوحة | 16,777,216 |
| إطارات الطلب | 21,600 |
| الطبقات | 16 |
| الأصول | 128 |
| مخرجات الإطارات | 65,536 |
| مفاتيح كل منحنى | 256 |

تُفحص أحجام القوائم قبل النسخ الدفاعي داخل منشئات المنحنيات والطبقات والطلبات والنتائج. هذه الأسقف حدود أمان للبروتوكول وليست قياسات أداء للهاتف أو موافقة تشغيلية لمحرك بعينه. لا يزال `WolfResourceGuard` والقياس المعتمد للمحرك وميزانياته شرطًا قبل أي إرسال إنتاجي.

## 4. سلامة المخرجات والبصمات

- فصل صيغة البكسل الخام عن ترميز الملف: `RGBA_8888/RGBA_F16` مقابل `RAW/PNG/WEBP/JPEG`.
- إضافة عدد بايتات كل مخرج وهوية Runtime/Adapter/Engine التي أنتجته.
- اشتراط بادئة `artifact:` لمراجع المخرجات، ورفض مسارات الملفات والروابط كمراجع مباشرة.
- إضافة `WolfSceneOutputArtifactVerifier`؛ يجب على تنفيذه حل المرجع داخل مساحة التطبيق الخاصة، وقراءة البايتات الفعلية وحساب SHA-256 وحجمها وأبعادها وبياناتها. لا يعتبر مدقق العقد بصمة نصية صحيحة دليلًا على سلامة ملف لم تُقرأ بايتاته.
- مقارنة البيانات المحسوبة من الملف الفعلي مع بيانات المخرج المعلنة.
- تنفيذ جميع فحوص البنية والنطاقات والبصمات وأحجام الملفات وتفرد المراجع أولًا؛ لا يُفتح أي ملف ولا يُستدعى `artifactVerifier` إذا فشل أي فحص بنيوي، وتُقرأ الملفات فقط بعد اجتياز النتيجة كلها مرحلة التحقق المسبق.
- التحقق من إجمالي حجم المخرجات، وحجم العناصر المحتفظ بها لإعادة الاستخدام، ومنع overflow في الجمع.
- اشتراط مطابقة هوية المحرك والمحول وإصداراتهما بين الطلب والنتيجة.
- جعل قوائم الطلب والنتيجة والتشغيل ونتائج التحقق نسخًا دفاعية غير قابلة للتعديل.
- استخدام أنماط تحقق ثابتة لهويات العناصر وبصمات SHA-256، ورفض مرجع artifact يتجاوز 137 حرفًا قبل إنشاء substring أو تمريره إلى verifier.
- حساب PTS المتوقع مرة واحدة لكل إطار ثم إعادة استخدامه عبر الطبقات؛ ومنع إعادة فحص صلاحية الجدول الزمني المكلف لكل مخرج.
- فحص قاعدة الكاميرا مباشرةً حسابيًا دون إنشاء متجهات مؤقتة أو أغلفة استثناء لكل إطار.

## 5. اختبارات الإصلاح

أضيفت تغطية لـ:
1. التوقيت الكسري ورفض تجاوز نطاق PTS.
2. رفض تجاوز PTS لنطاق Long، مع عدم استدعاء `BigInteger.longValueExact()` على Android.
3. مسارات الحركة للطبقات والكاميرا، والتحقق من صلاحية الكاميرا عبر نطاق الإطارات.
4. حدود أحجام اللوحة وعدد الطبقات والإطارات والمخرجات.
5. رفض بصمة لا تطابق البيانات التي أبلغ عنها قارئ الأصول بعد اجتياز التحقق البنيوي.
6. منع فتح أي ملف عند وجود بايتات/بصمة غير صالحة أو مرجع مكرر أو إجمالي تخزين يتجاوز الميزانية.
6. رفض نتائج محرك/Adapter لا تطابق الهدف المطلوب.
7. منع تغيير قوائم الطلب والمنحنيات والمخرجات بعد إنشائها.
8. رفض مخرجات تتجاوز حدود التخزين أو لا تحتوي نطاق الإطارات كاملًا.

## 6. حدود الملكية المحفوظة

- `StoryDirectorEngine` يظل مالك نية اللقطة وتكوينها وتوزيع ميزانية إطارات اللقطات.
- `OfflineMotionEngine` يظل مالك توزيع إطارات المشهد وحركة الكاميرا الحالية.
- WOLF Kotlin Core / Motion Hub يظل مالك مدة الفيلم وFPS والجدول الزمني وPTS والصوت والموارد والاسترداد والتركيب والتصدير.
- لا Adapter يغير القصة أو الخطة أو المدة أو الإطارات أو توقيت الصوت.
- `WolfAssetRegistry` هو صاحب قرار اعتماد الأصول؛ مرجع أصل في العقد لا يمنح الموافقة.
- لا تحميل DEX/JAR/SO أو سكربتات أو كود ديناميكي.
- لا اتصال إنتاجي بأي محرك في هذه المرحلة، ولا اختبار على Realme 7، ولا APK تجريبي.

يشغّل Workflow المرحلة 13 بناء Debug APK و`lintDebug` و`testDebugUnitTest` واختبارات Android instrumentation، إضافة إلى اختبارات Stage 11 المعزولة وKorGE وفحوص asset intake. لا يُرفع APK أو أي artifact نشر. نجاح كل Job يُثبت في نتيجة التشغيل الفعلية، ولا يُستنتج من وجود ملف Workflow.

**لا يوجد اختبار هاتف حقيقي أو اختبار Realme 7 في هذه المرحلة.**
